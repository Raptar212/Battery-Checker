# Протоколы и грабли (всё проверено на железе)

Эталоны: `research/probes/*.py` (Python + `hidapi`) и `research/probes/*.cs` (`dotnet run`).

### HID вообще
- WinRT `HidDevice` даёт десктоп-приложению без пакетной идентичности **только чтение** →
  открываем путь интерфейса через `File.OpenHandle` + `hid.dll` (длины отчётов из `HidP_GetCaps`).
- Чтение и запись — **два отдельных дескриптора**: один `FileStream` ставит запись в очередь за
  висящим чтением. `RandomAccess` не подходит — отвергает несеекабельные дескрипторы.
- Поиск по AQS — только с `System.Devices.InterfaceEnabled:=…#True`, иначе в выдаче старые интерфейсы.

### Logitech HID++ 2.0 (G602 через приёмник C537)
- Коллекции `0xFF00`: usage 1 — short (`0x10`, 7 байт), usage 2 — long (`0x11`, 20 байт).
  Писать в short, ответ ловить в обеих (у G602 приходит в long).
- Запрос `[0x10, idx, feature, (fn<<4)|SWID, p0, p1, p2]`; мышь — `idx 0x01`.
- **SWID меняется на каждый запрос (`0x0A…0x0F`)**: ответ не повторяет id фичи, и запоздавший
  ответ (мышь просыпается > 1 с) иначе засчитывается следующему запросу. Чужие SWID — G HUB.
- `root.getFeature(0x1000)` → индекс (у G602 = 5); `0x0005` DEVICE_NAME → «Wireless Gaming Mouse».
- Ошибки `0x8F` (1.0) / `0xFF` (2.0). Сон и выключение неотличимы → `Presence.SleepGrace`.
- **Точного заряда у G602 нет**: прошивка отдаёт только ступени 100/50/20/5 (`0x1000` fn 0:
  уровень, следующая ступень, статус); `0x1001` (напряжение) и `0x1004` нет. Проверено
  2026-11-16: со свежими батарейками — «50 %, следующая 20 %». G HUB видит то же; прошивка
  закрыта, менять её не будем. Это не баг программы.

### Astro A50 Gen4 (база, usage page `0xFF32`) — протокол [tdryer/eh-fifty](https://github.com/tdryer/eh-fifty)
- Запрос `[0x02, cmd]` до 64 байт → ответ `[0x02, status(2 = ok), len, data…]`.
- `0x54` → бит 1 = гарнитура включена; `0x7C` → бит 7 зарядка, биты 0–6 процент.
- База повторяет **последний** заряд при выключенной гарнитуре → сначала `0x54`.
- Опрос базы обрывов звука **не вызывает** (проверено по времени, см. память `project_bc1_open_items`).

### DualSense — по Linux `hid-playstation.c`
- BT `0x31`: статус в `r[54]`; USB `0x01` (64 байта): в `r[53]`. Младший полубайт 0..10 →
  `min(n*10+5, 100)`; старший: 0 разряд, 1 зарядка, 2 полный.
- **По BT заряд — только в режиме `0x31`.** Без него идут короткие `0x01` (даже с запущенным Steam,
  2026-11-16) → «—». Опция `DualSenseFullReports` (по умолчанию выкл., BC-12) сама переключает:
  чтение feature `0x05` (калибровка), как Linux и Steam; держится до переподключения. Риск —
  DirectInput-игры без Steam Input теряют геймпад, поэтому только по галочке. Проверено: 5 %, зарядка.
- `ReadFile` дополняет отчёт до `InputReportByteLength` (по BT 78): USB-отчёт — **ровно** 64 байта.

### Bluetooth (Classic и LE) — `BluetoothSource`
- Заряд — свойство PnP-узла `{104EA319-…} 2`: Classic — `BTHENUM\{0000111E…}…&<адрес>_C…`,
  LE — `BTHLE\Dev_<адрес>\…&<адрес>` (Windows сама читает GATT `0x180F`, сами в GATT не ходим).
- Windows хранит **последний** заряд и после отключения → связь из `BluetoothDevice` /
  `BluetoothLEDevice.ConnectionStatus`.
- Тип: Classic — Class of Device (периферия, бит 6 = клавиатура); LE — Appearance (`0x0F`/1 клавиатура).

### Keychron Link (приёмник `3434:D030`) — заряда нет
- Коллекция `0x8C`: input `0xB1`/`0x54`, output `0xB2`, feature `0x51`–`0x53`. Feature на чтение
  — ошибка, без запросов input-отчётов нет; VIA `0xFF60` у приёмника нет. Стоковая прошивка
  заряд по raw-HID не отдаёт (Keychron/qmk_firmware#471) → клавиатуру мониторим только по BT.

### Gtheos Captain 300 (донгл 2.4 ГГц `4C4A:4155`, чип Jieli) — заряда нет
- Интерфейсы: `MI_00` — USB Audio, `MI_03` — одна HID-коллекция consumer control (кнопки
  громкости). Вендорской коллекции `0xFFxx` нет, родной программы нет → канала для заряда нет.
- По Bluetooth (Hands-Free) заряд есть — читает общий `BluetoothSource`.
